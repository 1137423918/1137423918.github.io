CANCELLATION / CALLBACKS / 2026.11.21

取消任务时，
别让清理回调等住自己的锁。

长任务需要可靠的取消与资源清理。AutoGen 的 CancellationToken 在持有非重入锁时执行回调；清理回调若查询取消状态、注册另一个清理回调，或等待另一个读取 token 的线程，就可能被这把锁挡住。

在授权服务器 CPU 上完成公共 API 与真实 AgentRuntime 复现。候选完整核心包测试 233 项通过。上游已归档只读，创建 PR 被 GitHub 拒绝；修复保留在个人 fork，没有新 AutoGen 上游 PR。

一个会卡住的公共调用

token = CancellationToken()
token.add_callback(lambda: print(token.is_cancelled()))
token.cancel()

取消已经发生，回调本应读到 True 并返回。但原版 cancel 持锁调用回调，is_cancelled 又尝试获取同一把锁。给已经取消的 token 登记回调时，原版 add_callback 也会在锁内执行它。

回归还覆盖回调等待另一个线程读取状态的情况；即使仅换成 RLock，另一个线程仍不能取得尚未释放的锁，因此需要调整回调的执行范围。

保留状态互斥，释放锁后执行回调

候选在锁内确认取消状态并复制回调列表，再释放锁逐个调用。回调登记也只在锁内判断状态或保存；已经应当执行的回调离开锁后调用。future 关联复用同一登记路径，保持重复取消不重复执行。

lock: set cancelled, snapshot callbacks
unlock
invoke callbacks

回调仍同步执行，也仍可能自身阻塞或抛异常；没有新增回调超时、异常隔离或强制终止线程。跨线程调用 asyncio Future.cancel 的循环归属问题另有 PR #8359，本候选没有冒称解决它。

七项新增检查包含在 233 内，其中一项 future 兼容检查在原版也通过。两个测试范围不同，没有声称原版完整 233 项的前后对照。三项警告来自既有的可信 FunctionTool 配置加载提示，保留在日志中；没有运行整个多包、操作系统和 Python 版本矩阵。

公共复现驱动启动实际 SingleThreadedAgentRuntime，等待一个受控请求进入处理器，再调用带清理回调的取消流程。原版输出 agent_waiting 和 cleanup_entered 后卡住，线程栈定位到 is_cancelled；驱动在 20 秒预算后回收自有子进程。候选完成一次清理、取消请求与处理器，并关闭运行时。

两者使用相同驱动和最终解释器。等待任务是受控构造，SDK 和运行时是真实实现；没有神经模型、付费 API、GPU 或外部 Agent 服务。原版耗时被超时截断，不能计算加速比或吞吐提升。
