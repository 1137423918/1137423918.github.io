把 CPU 接进
真实维护任务。

没有空闲 GPU 时，我把固定版本 Qwen3-4B 转换为约 2.50 GB 的 Q4_K_M GGUF，用官方 llama.cpp CPU 运行时接入维护运行器。模型在真实 Deep Agents 源码上执行了正常与检查点恢复两种场景；两种场景都达到预定时限，尚未交付通过验收的补丁。

同一个公开问题，两种运行方式。模型接收问题和两条虚拟文件路径，没有收到脚本计划或参考补丁。原版任务、旧失败和不可编辑的 28 个验收契约均保留。

保存下来的执行过程

场景实际墙钟模型回复 / 工具结果补丁验收
正常运行600.115 秒8 / 9未导出，未进入验收
检查点中断后恢复600.032 秒12 / 13未导出，未进入验收

中断发生在两次 ls 查询完成后，恢复后继续执行了 glob、读取和 grep。最后检查点中保存 13 条工具结果；这是导航状态续跑的证据，完整维护任务验收仍未通过。

服务共记录 22 个模型任务启动、2 个取消，检查点中保存 20 个模型回复。取消部分没有完整回复，已保存 usage 不能当作完整 token 或成本统计。提示缓存启用，节点还承载其他任务，这里不作通用加速比或恢复收益的因果比较。

失败样例也需要可审阅

正常场景在虚拟区把原先 47,177 字节、1,250 行的模块写成了 900 字节的单行文本。写入参数保留字面的反斜杠 n，静态 Python 语法解析失败。该文本作为未导出、未执行的失败样例保存，没有当作有效修复。

恢复场景最后没有改动两份虚拟文件，期间出现一次 read_file 工具错误。工具操作数、状态得到保留以及模块被修改，都需要与最终验收分别判断。本轮没有延长场景预算，也没有补跑后重记旧结果。

一份固定身份的环境

后端固定到 llama.cpp b12576 的 4783b1145；原始模型 revision 为 cdbee75f。转换后重新校验 12 个原始文件，约 8.06 GB 全部匹配。派生模型有 398 个 tensor、4,022,468,096 个参数；内嵌模板哈希与固定 HF tokenizer 相同。

模型、原生二进制、依赖库和任务都绑定哈希。已有运行库不足时，依赖只解压到本任务目录，系统与其他项目环境保持原状。模型初始虚拟文件已核对来自未修复的 744a797e，没有读入 checkout 中保存的操作者候选修复。

服务仅监听服务器回环接口，显式关闭 GPU offload：4 个计算线程、4 个预填充线程、1 个 HTTP 线程、1 个 32K slot、nice 19。启动器有内存和墙钟限制，3 项 Linux 进程检查覆盖哈希拒绝、超时清理以及记录写入失败后的子进程回收。它们是独立进程检查，不是模型任务成绩。

试验结束后已核对进程身份并关闭服务，原生子进程正常退出。0.5 秒采样的最大 RSS 约 8.47 GiB，是该服务的采样值，不能代表整台节点的峰值。
