REAL MODEL / CPU / 2026.11.21

换了模型之后，
先看请求预算。

没有空闲 GPU 时，在服务器以四线程 CPU 运行固定 Qwen3.5-9B Q4_K_M，尝试修复 Deep Agents 的真实路径规范化问题。沿用固定原版测试和语法导出保护，只更换模型预设与声明采样；正常和检查点恢复两种场景都实际执行。

两场均因单次请求 180 秒超时失败：没有虚拟文件改动、导出补丁或官方验收。这是同一个公开问题的两个运行场景，不能当成通用修复率，也不能隔离出模型能力与 CPU 资源的影响。

区分请求超时与场景上限

场景总耗时保存的模型回复 / 工具结果结果
正常185.324 秒0 / 0单请求超时
检查点恢复376.219 秒2 / 4单请求超时

每场 600 秒、40 个图步骤，每次请求最多生成 1536 token、180 秒、零重试；没有追加修复轮次或事后延长预算。两场未到 600 秒上限，均以 OpenAITimeoutError 退出。

普通运行仅处理 2442 个提示 token 就用了 172.58 秒。原生服务共启动四个请求：两个完整回复、两个取消；最后一个请求在 154.67 秒时只观察到 2048 个提示 token、约 67% 进度。可观察的瓶颈是当前 CPU 配置下的提示处理与请求预算，不能据此评价该模型的一般编程能力。

恢复了读取状态，还没有发生编辑

恢复试验先实际完成两次 read_file，再由驱动 SIGKILL worker。使用相同运行目录续跑后，又完成两次分段读取。只读检查最终数据库确认：两条模型回复、四条成功读取、零虚拟内容改动。没有发起额外生成来审计检查点。

这支持读取状态保留与继续执行；没有验证已编辑文件恢复或完整维护成功。两个场景按顺序共享同一服务和提示缓存，恢复场景受益于热缓存，耗时不能作冷启动或恢复开销的控制对比。

把模型身份和运行条件固定下来

量化文件来自 lmstudio-community，固定 revision 1379f25c，大小 5,627,044,256 字节，逐字节 SHA 与官方托管元数据匹配。只读 GGUF 检查得到 qwen35 架构、427 个张量、约 89.54 亿参数；聊天模板与固定原版模板哈希一致。

量化方注明 Qwen3.5-9B 来源，但未给出精确原权重 revision。本次抓取的官方模型卡与配置仅是参考身份，不冒称已验证权重转换血缘。运行时为未改动的官方 llama.cpp b12576，文本模式、禁用思考、无视觉投影器、零 GPU 层。

采样显式声明 temperature 0.7、top_p 0.8、presence_penalty 1.5、top_k 20、min_p 0、repeat_penalty 1、seed 42。1536 token 的短工具回合上限不同于厂商长推理条件；新模型、采样和受保护验收与旧 4B 试验同时变化，不作因果提升结论。

工程验证和清理也保留失败事实

实际生成前，服务器完整 57 项项目检查为 43 通过、14 跳过（该环境缺少 jsonschema）；包含新增的显式采样 HTTP 传输检查。假服务检查只验证接口，不计作神经维护成绩。验收策略已配置，但没有候选补丁进入验收。

模型服务只监听 loopback，限制四线程、48 GiB 地址空间、36 GiB RSS 和总运行时限。结束后核验自有进程身份并向启动器发送 SIGTERM；原生子进程没有在十秒宽限期内退出，最终被 SIGKILL 回收。已确认端口关闭、两个进程消失，不把强制清理写成正常退出。最初检查命令漏写依赖库目录的 /lib 导致失败，修正参数后才开始生成，该失败日志也保留。
