任务中断之后，
如何继续？

软件维护任务需要编辑文件、执行测试并交付补丁。进程意外退出后，重新执行所有工具可能覆盖人工修改，也会让已经完成的步骤失去记录。我在 Agent Reliability Lab 中实现了一条可恢复的维护流程，并在真实的 Deep Agents 仓库验证。

首轮验证采用固定脚本工具计划，衡量执行基础设施。正常运行与三处真实 SIGKILL 中断后恢复均通过；随后已运行真实 CPU 模型尝试，均无补丁；结果另行记录。

一个可以交付补丁的工作流

  1. 固定目标仓库 commit、允许编辑的文件和验证命令，生成任务哈希。
  2. Deep Agents 在 StateBackend 编辑虚拟文件；LangGraph SqliteSaver 持久化工具结果。
  3. 把修改落地到任务专属 Git worktree，生成真实 diff，检查文件范围与人工修改冲突。
  4. 执行预设测试，记录退出码、超时和日志哈希；通过后输出 ready_for_review 与补丁。

同一运行目录使用文件锁限制单个 worker；恢复时核对任务定义，成功任务重放会检查补丁是否被改动。最终结果供人工审阅，运行器不会自动提交、推送或合并。

项目自身的验证

首轮服务器验证的 33 条项目测试全部通过，包括 8 条证据测试、15 条运行器测试和 10 条使用假 HTTP 服务的传输与修复流程测试。检查了重复执行、并发抢占、任务变更、文件越界、人工修改冲突、测试失败、验证子进程组超时终止、跨重启图步数预算，以及完成后补丁被篡改的情况。

执行环境为 Linux、Python 3.11.4、Deep Agents 0.7.41、LangGraph 1.2.24 和 SQLite checkpoint 3.1.3。实验只使用 CPU；共享存储冷导入超时的首次失败保留在私人实验记录，随后使用独立 home 环境完成验证。

目前能够说明什么

结果支持这一个固定维护任务在已测阶段边界中断后，恢复并产生同一份通过测试的补丁。还需要加入更多任务、真实模型与更多故障点，才能评估任务完成率和恢复开销。

  • 当前仅支持允许列表中的既有 UTF-8 普通文件。
  • 已覆盖阶段边界与验证进程运行中仅杀 worker PID。整机断电、监督进程自身被 SIGKILL、子进程脱离原进程组尚未验证。
  • 测试命令由操作者明确提供，环境不作为恶意代码安全沙箱。
  • 崩溃恰好发生在命令结束与结果落盘之间时，测试可能重跑。外部副作用不保证 exactly-once。
  • 图步数预算跨重启保存；它不等于 token 或费用上限。

验证运行时，只杀 worker 会怎样？

新增回归在首版实现上失败：worker 被单独 SIGKILL 后，运行锁已经释放，验证命令及子进程仍在运行。这会让新 worker 与旧验证同时使用工作区。

修复后，由独立监督进程持有同一把运行锁，并通过管道 EOF 检测 worker 消失。它在命令结束、超时或 worker 退出时清理验证进程组，再释放锁。验证命令不会继承监督管道和锁。

同一真实 Deep Agents 任务上，实验先观察到匹配预设 argv 的 pytest 进程，再只杀 worker PID。旧验证在锁释放前被终止；随后恢复重新执行验证，119 条测试通过。正常参考运行也通过 119 条，补丁哈希相同。固定工具计划与任务定义均未改变。

测试失败之后，如何继续修复？

单份补丁没有通过验收时，新增流程可以把失败返回给下一轮，从上一份候选继续修改。额外轮次默认 0，可显式限制为 0–3 次；每轮保留独立检查点、工作区、补丁与日志。反馈使用最多 8 KiB 日志尾部，并绑定补丁与日志哈希；验收配置由操作者固定。恢复时复用经过核验的失败记录，不因内存计数丢失而重新开始。

在真实 OpenHands 仓库上，参考计划首先只增加历史读取方法，故意留下撤销顺序问题。首轮 184 条旧测试通过，但真实只读目录验收失败。下一轮从失败候选继续完成修复，184 条与权限验收均通过。正常执行和反馈落盘后仅杀父进程的 SIGKILL 对照，都在第二轮完成，输出同一份 1,795 字节补丁；恢复前后首轮日志哈希相同，证明这次恢复没有重跑已完成的失败验收。

第三个真实维护仓库：Google ADK

继 Deep Agents 与 OpenHands 编辑器任务后，同一编辑运行器新增 Google ADK 文件产物清理任务。只有一份生产文件可编辑；固定原版测试副本与四个操作者契约，分别检查缺失文件、权限错误与嵌套产物保留。

正常运行及首次工具检查点、补丁落地后、验证前三处 SIGKILL 恢复，均完成三次编辑，输出相同补丁；四场生产代码都与此前验证的候选修复字节一致。各通过 1863 条原版测试（26 条预期失败）与四个外部契约，整组用时 470.386 秒。重复场景和既有上游回归不累加为新测试成绩。

这是明确参考计划的运行器验证，不是 ADK agent runner 适配器或神经模型自主修复。独立模型任务已准备、未运行。原有计时器允许 180 秒观察中断阶段，再给恢复 worker 600 秒，不能称严格的合并 600 秒上限；本次四场合计仍小于 600 秒。完整证据保留负对照、真实强杀轨迹和固定测试哈希；复现与边界说明全部口径。

只读查看真实运行进度

直接读取某个SQLite checkpoint tuple曾遗漏增量消息。新增agent-lab-inspect通过同一图结构的get_state重建进度，只使用空脚本模型构造schema，不执行模型、文件工具、恢复、Git或验收。可在运行时查看，也可复查失败轨迹。

输出最多8KiB UTF-8元数据：模型回复与工具结果数量、待执行节点、工具名计数、虚拟文件字节和SHA；不输出任务提示、参数或源码。checkpoint使用一个只读事务；工件状态是另一个瞬间的观察，不表示测试、补丁或验收重新核验。

完整服务器90项通过、零跳过，包含八项本次检查。真实任务早期读到一份回复、两条工具结果和两个索引标记；wheel入口稍后读取到两份回复、三条结果。两个已有参考检查点的持久数据保持，均未重新推理或验收。这些数字不增加模型修复成绩。

SQLite只读连接仍可能创建空WAL/SHM协调文件。核对发现旧状态目录是nfs4；SQLite WAL不支持网络文件系统，旧观察不能作为这种部署的可靠性保证。后续新任务须先落到本机受支持的状态存储，并补充启动预检。

验证退出后，独立会话子进程仍在运行

最新CPU工程检查复现了一个真实缺口：验证命令退出0，它另建会话的子进程仍在后台。Linux独立监督器现在接管孤儿子进程，停止并回收它们后才释放worker锁；覆盖新会话与双重fork，不依赖全系统PID快照清理。

首版两个独立检查通过，但三个worker集成检查失败：过滤PYTHONPATH后，模块启动命中了服务器已安装的旧监督器。最终改为启动worker自身已加载的监督器绝对文件路径，验证命令仍使用过滤后的环境。前一版失败和源码保留。

服务器定向5项通过，完整108项通过、零跳过；新增2项包含在完整总数内，另有3项旧检查加强为独立会话子进程。双重fork作业已回收；超时清理未误杀无关进程；worker被SIGKILL后，旧作业清理完成才允许恢复。完整用例耗时319.701秒，受监控阶段墙钟322.778秒。

这是工程回归，没有模型推理、GPU占用或新的自主修复成绩。Linux之外仍沿用进程组清理；不是恶意代码沙箱，也不覆盖监督器自身被强杀。内核不可中断等待可能继续持有运行锁，不能承诺硬性清理时限。
