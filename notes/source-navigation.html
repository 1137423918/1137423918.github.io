上一轮真实 CPU 维护尝试中，模型读取了生产文件前 400 行，仍停留在常量表。两个相关函数实际从第 822 和 846 行开始。请求的大部分时间消耗在提示处理，这促使我改进源码定位与上下文选择。

本轮实现并验证一个可选源码工具，没有运行新的神经推理。真实仓库控制使用明确的目标符号与参考编辑计划；不把它写成模型自主定位、修复成功或性能提升。

索引当前状态，而不是旧 checkout

inspect_python 从当前检查点内的虚拟文件生成 Python AST 索引，列出函数、类、异步方法和嵌套定义，标明装饰器在内的行范围。重复定义保留独立的位置 ID，随后可按 ID 读取对应源码；工具没有宿主文件、导入或命令执行能力。

每个结果带当前内容的 SHA。读取符号和继续分页都要提交同一哈希，编辑后旧请求会明确拒绝。每次从当前内容重新解析，无需维护可能过期的索引缓存；恢复后也不会偷偷读取原版内容。

响应预算与额外开销都算清楚

每页最多 8192 UTF-8 字节，保留有效 JSON 和 next_offset，不把中文字符数量误当字节。单行过长无法装入时明确返回错误；非 Python、语法错误或索引不包含的内容仍可使用已有 grep/read_file。AST 不是完整的语义依赖索引。

固定真实源码中，由操作者选定两个目标函数：完整索引加两个源码页合计 11127 字节，单页最大 4766 字节。新增工具的 OpenAI schema 另占 988 字节，还不包括系统提示与会话历史。仅看片段字节数无法声称净 token、成本或耗时节省，也没有测量模型会如何选择工具。

编辑后中断，恢复后查到什么

固定 Deep Agents 基线 744a797e，用既有参考计划编辑生产文件；在第一条工具结果保存后实际 SIGKILL worker，再使用相同任务与目录恢复。恢复后的源码工具哈希必须与最终已编辑文件一致，而非原版 blob。
